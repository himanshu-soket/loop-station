The pretraining data pipeline

A complete, navigable explanation of the pretraining data architecture — every phase, stage and component, how they connect, what each one consumes and produces, and which parts are already implemented.

5 phases8 stages49 components9 cross-stage links sources: architecture document + codepipe

Executive overview

The pretraining data pipeline turns raw, messy source material into training-ready token shards. Four kinds of input — web crawls, compiled open datasets, binary documents and audio — are normalised into one format, passed through a cheapest-first quality gate, deduplicated at three granularities, scored by small models for quality and domain, and finally tokenized into Megatron's memory-mapped format.

What it does

Converts heterogeneous raw sources into a clean, scored, deduplicated corpus, then into shuffled, mixture-weighted token shards that a pretraining run can stream directly.

Why it exists

Model quality is dominated by data quality. Every phase removes a specific kind of harm — boilerplate, duplicates, personal data, benchmark contamination, low-value text — before GPU tokens are spent on it.

Primary objectives

  • One format. All sources converge to WARC, then Parquet — new sources never change downstream code.
  • Cheap first. URL filters run before language ID; language ID runs before model scoring.
  • Never destroy. Removals are logged per reason, so thresholds can be tuned by reading what was dropped.
  • Designed mixtures. Quality and domain scores become sampling weights, not just cuts.

How the phases fit together

  1. 01 Ingest — four parallel paths produce WARC shards + URL lists
  2. 02 Filter — all shards converge through one quality gate → Parquet
  3. 03 Dedup and clean — URL/exact/MinHash dedup, PII masking, decontamination
  4. 04 Classify — quality + domain scores as columns
  5. 05 Tokenize — mixture-weighted Megatron .bin/.idx output
Two tracks, one report. The five-phase architecture below is the documented design of the EKA pretraining pipeline (its interactive map ships in this console). Alongside it, the codepipe project — the implemented code-corpus pipeline on this machine — already builds several of the same steps. Component cards carry a cross-reference badge where codepipe has a counterpart: Implemented means the code exists and runs; Planned means it appears in codepipe's roadmap but is not built.

02

Filter

.warc → .parquet · 10 components across 1 stages
Quick read
What it does

Runs the cheapest-first quality gate over every WARC shard: domain blocklist, HTML boilerplate extraction, language identification, then Gopher, C4 and FineWeb heuristic filters.

Why it matters

Bad data is dropped before expensive compute is spent on it, and every byte passes the same quality bar regardless of which source it came from.

Primary input

WARC shards from all four ingestion paths — they converge at the WebArchive shards input

Primary output

<ROOT>/filtered/<SOURCE>/ — clean text as Parquet shards with metadata columns

Dependencies

Phase 01 Ingest (all four stages feed the filtering input).

Applies the tokenizer, samples and shuffles by mixture weight (source, domain, quality), splits train/validation, and writes Megatron's memory-mapped .bin/.idx shards.

Branching

Two branches exist, both in Phase 01: the crawler and compiled-sources type selectors route HTML to WARC shards but send PDFs/DOCX/notebooks to URL lists, which feed Document extraction. Audio never branches — ASR output goes straight to WARC.

Parallelism

Crawl workers scale horizontally (Worker 1…n share a URL queue); filtering, dedup and classification all operate per-shard or per-language, so each stage parallelises without coordination.

Convergence

All four ingestion paths meet at one node — WebArchive shards (f_in). From there the pipeline is strictly linear through the phases.

No feedback loops

Data flows forward only. Tuning is done by re-running earlier stages after reading removal reports — the architecture has no automatic back-edge.

Named external tools

Trafilatura (HTML extraction) · fastText / IndicLID (language ID) · Whisper / IndicConformer (ASR) · an LLM corrector and an LLM labeller for classifier training · MinHash + LSH via datatrove-style banding · the Megatron indexed-dataset format.

Storage contract

Every phase writes sharded outputs under <ROOT> keyed by source: raw/, filtered/, preprocessed/, classified/, tokenized/megatron/. Intermediate formats are WARC (ingest) and Parquet (everything after filtering).

codepipe (implemented sibling)

~/soket/codepipe builds stages 0–3 for a code corpus: inventory.py, filter.py, exact_dedup.py, minhash.py, report.py, with shared I/O in storage.py and all thresholds in config.py. Its roadmap (stages 4–6) covers PII/decontamination, the quality classifier and split/mixture/tokenization.

Not present

No scheduler, orchestration service, database or monitoring stack is part of this architecture — execution is staged commands writing to a filesystem, resumable via task markers.

Monitoring, validation and troubleshooting

Only mechanisms that actually exist in the sources — EKA design and codepipe implementation alike.

Removal reasons (design)

Every filter logs why each document was removed. The architecture's own tip: “Log documents removed per filter per source. It's your best debugging table.”

codepipe: _done markers + report.md

Each finished task writes _done/tNNNNN.json with per-language in/kept/removal counters; python -m codepipe.report <stage_dir> renders them into report.md (docs in/out/kept, bytes, removal reasons by share, per-language table). This console's Pretraining DataTrove view aggregates the same markers live.

codepipe: removed/ samples

The filter stage saves a fraction of removed files with content and reason (--save-removed, default 1%) so bad removals can be read by hand.

codepipe: resume model

Finished tasks are skipped on re-run; failed tasks are simply re-submitted. Work folders (02_exact/hashes, drops, 03_minhash/work) can be deleted once a stage is verified.

Finding a failure

Locate the phase by artifact: missing .warc → Phase 01; missing filtered Parquet → Phase 02; duplicate rows surviving → Phase 03; wrong scores → Phase 04; training data issues → Phase 05. In codepipe, check the stage's _done/ count against --num-tasks.

Validation gates (design)

Decontamination keeps the removed list “as evidence of eval integrity”; the held-out split (Phase 05) exists to monitor overfitting; per-segment ASR confidence and edit-distance rejection guard the audio path.

Glossary and quick reference

WARC
Web ARChive (ISO 28500) — the raw-capture format all ingestion paths normalise into.
Parquet
Columnar compressed storage used from filtering onward; scores are added as columns.
MinHash / LSH
Compact similarity fingerprint + locality-sensitive hashing that groups near-duplicates without pairwise comparison. Here: 5-gram shingles, ~112 hashes, 14 bands × 8 rows.
Jaccard
Set-similarity measure; the banding parameters target ≈0.75–0.8, i.e. “near-duplicate”.
Union-find
Cluster algorithm joining candidate pairs transitively (A≈B, B≈C ⇒ one cluster).
Gopher / C4 / FineWeb
Named heuristic filter families from the C4/Gopher/FineWeb corpus papers: document-level stats, line-level rules, and extra ratio heuristics respectively.
LID
Language identification (fastText, IndicLID) with a confidence threshold.
PII
Personally identifiable information — masked with typed placeholders like <EMAIL>.
Decontamination
Removing n-gram overlap with evaluation benchmarks so scores stay honest.
Megatron .bin/.idx
Flat token binary plus document-offset index; memory-mapped zero-copy reads for training.
EOS
End-of-document token inserted during tokenization.
Mixture weights
Sampling weights by source/domain/quality applied before the global shuffle.
codepipe
The implemented code-corpus pipeline (~/soket/codepipe) that builds several Phase 02–03 steps for code data.
EKA modules
EKACrawler, EKAProcessor (+ PreProcessor / Document Processor), EKAClassifier, EKATokenizer — the architecture's stage owners.
S1–S7
Step tags used inside Phase 03 (URL dedup … Decontaminator).
