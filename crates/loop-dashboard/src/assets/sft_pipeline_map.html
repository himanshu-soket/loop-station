Where rejected rows go

Every row a step does not pass on lands in one of four places. The bins fill as the run reaches each step. Tap a coloured pill on any step to see why it was rejected and how to repair it.

Repair routes

How each kind of rejected row is repaired and the step it re-enters. Re-running a level is safe: every step writes a new folder and resumes on Slurm.

FateWhat it meansHow to repairRe-enters at
fixedA repairable problem. The step repairs the row itself and passes it on.Nothing to do. The fix is re-checked downstream: s13 checks language and identity of L4 fixes, s15 verify re-runs every detector. The original is kept in _rejected/originals/.Next step, automatically
reviewA rule cannot decide alone, or a whole source failed to map.The data owner reads the report. Decision 1: drop → add row ids to DRISHTI_DROP_LIST (s15) or a POST_DROP flag (s16). Decision 2: keep → no action. Decision 3: the source needs code → write or extend the L1 adapter. · ·
quarantineBroken, unsafe, wrong, contaminated, a duplicate or another model's identity. Never trained on.Not repaired row by row. If a sample shows the rule was wrong (false positives), fix the rule or threshold in common/config.py or the L1 rules, then re-run that level; it reads its input folder again. Contaminated rows are never brought back.The same step that removed them
reservoirValid but not chosen: outside the judge pool, above a quota, or below the selection bar this batch.Nothing is wrong with the row. The next batch pools rows never judged before; rows already judged keep their scores and can be selected if quotas change. October batches 2 and 3 came from here. (next batch)
